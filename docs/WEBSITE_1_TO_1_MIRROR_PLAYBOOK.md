# 网站 1:1 复刻与 GitHub 部署操作规范

> **默认目标：复刻原网站本身，不是以原网站为灵感重新设计一个网站。**
>
> 用户说“1:1 复刻”“原样复刻”“镜像网站”时，默认按本文执行。不能把主题相似、布局相近、手工重画部分组件称为 1:1 复刻。

## 一、什么才算 1:1

优先复用原站真实资源和页面实现，目标是在相同视口、相同页面状态下尽可能获得一致的视觉与行为：

- HTML / DOM 结构、文本、导航和页面层级；
- 原站 CSS、设计 token、字体、图标、图片、背景图、SVG、动画和媒体；
- 原站 JavaScript、图表库、交互行为、路由、筛选和状态切换；
- 原站公开数据文件、数据格式、数值格式化、图表和 tooltip 逻辑；
- 桌面与移动端的断点、滚动行为、悬停状态、键盘交互及浏览器历史行为。

以下做法**不算** 1:1 复刻：

- 看一眼网页后重新写一张“风格相似”的首页；
- 自行创作原站没有的文案、组件、插画、图表或动画；
- 用手写/随机/估算数据冒充原站数据；
- 用静态截图替代原本应当可交互的界面；
- 只复刻首屏而忽略页面底部、其他标签页、弹窗、菜单、筛选器和响应式状态；
- 在未比对原站的情况下声称“像素级一致”。

## 二、标准工作流

### 1. 固定复刻基准

1. 记录原站 URL、目标 GitHub 仓库、默认分支和部署平台。
2. 使用浏览器打开原站，检查登录前可访问的页面和全部导航入口。
3. 记录主要页面状态：首屏、滚动后、菜单展开、标签切换、筛选/搜索、图表 hover、移动端视口等。
4. 选定一致的基准视口（例如 1440×900），并保存原站截图作为对照；有条件时也记录移动端尺寸。
5. 判断哪些内容是公开可复刻的，哪些依赖登录、私有 API、服务器状态或授权资源。遇到访问限制时如实记录，不要猜测或伪造。

### 2. 先取原站资源，再决定怎么部署

先检查 HTML 中引用的 CSS、JS、字体、图片、SVG、manifest 等文件。随后查看 JavaScript 中的真实资源路径和数据加载逻辑：

- 识别原站是静态构建、客户端应用还是服务端渲染；
- 如果 JS 里指向版本化静态目录（例如 `data.<hash>/`），应检查并同步该目录中的 JSON 文件；
- 如果使用 API，必须从原版代码、浏览器网络请求或真实响应确认准确路由、查询参数、请求头及数据格式，不能猜测 API 路径；
- 递归下载 CSS 的 `url(...)`、`@import`、JS 动态加载资源和字体文件；
- 尽可能保持原始文件内容、文件名和目录结构。对哈希文件名、大小写、查询参数及相对路径尤其谨慎；
- 下载后检查文件类型、大小、响应状态和内容是否真的是预期资源，而不是 404 HTML 或访问拦截页。

**原则：原站源码可获取时，先原样复用原站 HTML/CSS/JS；不要先造一套替代界面。**

### 3. 为目标托管平台做最小适配

优先选择改动最少的路径：

- GitHub Pages 用项目路径发布时，要核实根相对路径（如 `/assets/a.js`）是否会错误指向域名根目录；
- 优先调整部署 base path、构建配置或必要的资源引用；避免大范围重写原始页面；
- 如果页面通过 hash 路由工作，保留原始 hash 路由和浏览器前进/后退行为；
- 如果存在 CSP、跨域、cookie、localStorage、Service Worker、动态 import 或 JSON fetch，逐项测试部署后的真实行为；
- 如果原站依赖不可公开的后端 API 或登录态，GitHub Pages 无法执行该后端。应在“部署真实后端/代理”“使用明确标注的固定数据快照”之间作出技术选择，并明确静态快照不会实时更新；
- 不得悄悄以虚构内容替代失败的数据接口。抓取或校验失败时应让构建失败并输出明确错误。

若只有公开的静态资源能够复用，应保留原版脚本和实际数据文件；如需编写路径适配器，只处理必须处理的路由或 base path，不要重写原站的界面和数据渲染逻辑。

### 4. 建立可重复的镜像与部署流程

推荐在仓库中保存：

- 原站镜像同步脚本（例如 `scripts/mirror_official_site.py`）；
- 原站 HTML、样式、脚本及相关媒体资源；
- 原站公开的静态数据快照（若原站本身就是静态数据驱动）；
- 数据/资源清单（来源 URL、同步时间、文件大小、失败记录）；
- GitHub Actions 工作流：同步资源 → 校验 → 提交（如有变化）→ 构建/打包 → 部署；
- README：原站地址、镜像地址、同步方式、部署方式及限制说明。

工作流应做到：

1. 使用明确的权限和正确的 Pages 部署方式；
2. 只有在必需资源抓取与校验通过后才部署；
3. 避免自动生成的同步提交无限循环触发；
4. 原站 hash 文件名或资源清单变化时能正确识别；
5. 原站不可用、资源缺失或 JSON 无法解析时，失败要清晰可诊断；
6. 部署后报告可访问 URL 和对应的源代码提交。

### 5. 复刻验收：视觉和功能分开验证

#### 视觉验收

在相同浏览器、视口大小和页面状态下，将原站与镜像站截图并排比较。至少检查：

- 页面宽度、容器边距、栅格、列宽、间距与对齐；
- 字体文件是否加载、字体粗细、字宽、行高和字距；
- 颜色、边框、圆角、阴影、渐变、图标尺寸；
- 图表尺寸、轴线、刻度、图例、数据点和 tooltip；
- 首屏与整页高度、滚动区域和固定/粘性元素；
- 桌面端与移动端断点；
- hover、focus、selected、disabled、loading、empty 等状态。

发现差异后优先确认是资源未加载、路径错误、字体缺失、视口不一致还是源站内容已变化；修复根因，而不是添加另一套视觉设计。

#### 功能验收

逐项验证：

- 每个导航入口、标签、按钮、菜单、筛选、搜索和图表交互；
- 页面 hash/URL 是否按原站改变，刷新后能否恢复正确状态；
- 浏览器前进/后退；
- 控制台错误、网络 404、CORS、字体和资源加载错误；
- 指标数值与原站数据文件一致；
- 原站使用的偏好设置是否保存和恢复；
- 页面在刷新及移动端加载后是否正常。

如无法实际运行浏览器自动化或截图比对，明确列出未验证项目，不得声称已完成逐像素验证。

### 6. 发布与线上检查

1. 推送代码到目标仓库，不另建临时项目替代用户指定仓库。
2. 确认 GitHub Pages 设置正确（通常使用 GitHub Actions 作为 Source）。
3. 检查 Actions 中同步、校验、构建、上传和部署步骤是否都成功。
4. 打开实际部署 URL，而不仅是检查 Actions 绿色状态。
5. 检查线上 HTML 引用的每个 CSS/JS/字体/数据文件都返回正确资源。
6. 对比线上页面和原站；若部署版本、缓存或 base path 出错，应修复后重新部署。
7. 最后分别说明：提交链接、部署链接、实际验证结果，以及仍然存在的限制。

## 三、MiMo RL 复刻案例中确认的经验

这次 MiMo RL 原站的正确路线是：

1. 获取 `https://mimo.xiaomi.com/rl/` 的真实 HTML；
2. 从 HTML 中发现并下载带 hash 的原版 CSS、JS、SVG favicon 和 Inter 字体；
3. 阅读原版 `app.*.js`，确认它使用静态目录 `data.04135c89/`，而不是猜测 `/api/...`；
4. 按原站的准确文件名下载 `runs.json`、`notices.json`、`benchmarks.json`，以及 Pro/Flash 各自的 `status`、`live`、`tags`、`series` JSON；
5. 保留原版应用脚本、Canvas 图表实现和数据格式化逻辑；
6. 仅为 GitHub Pages 做必要的路径处理；
7. 校验资源与 JSON，再上传 Pages，并检查 Actions 的完整结果。

本案例的关键教训：**不能因为已经写出一个能看的仿制页面，就把它当成用户要求的复刻结果；也不能只根据资源文件名猜测原站架构。必须先读真实源文件，再按实际依赖镜像。**

## 四、默认原则与例外

以后处理“复刻某网站”的任务时，默认直接执行本规范，无需用户再次强调：

- 目标是原网站本身，而不是重新设计的新网站；
- 首选原站真实源码和资源；自写代码只用于必要的兼容适配；
- 真实数据优先；任何快照、替代或缺失都必须明确标注；
- 在部署前后做可核验的视觉和功能检查；
- 诚实报告完成程度，未做截图对比就不宣称像素级 1:1。

如果原站无法访问、资源受访问控制、只有截图而没有源文件，或其后端功能无法在目标托管平台复现，应明确说明具体阻碍和可实现的复刻范围；不能把“无法完全复现”偷换成“创建一个相似网站”。
